Fuerza bruta ofensiva contra un login web

Apunte de laboratorio autorizado — práctica con DVWA (Damn Vulnerable Web Application) · Power fuerza-bruta-login

Alcance y autorización. Este apunte asume un laboratorio propio o explícitamente autorizado (p. ej. DVWA desplegado localmente o en un engagement con scope.yaml firmado). Todo comando de este documento se ejecuta solo contra objetivos declarados en la Allowlist_Objetivos del engagement. No usar estas técnicas contra ningún sistema sin autorización explícita por escrito.

1. Tipos de ataque de fuerza bruta

Antes de atacar, hay que decidir qué variante de fuerza bruta aplica al objetivo. Las tres relevantes para un login web como el de DVWA:

TipoQué haceCuándo usarla
Diccionario Prueba contraseñas comunes o por defecto (admin, 123456, password) contra una o pocas cuentas conocidas. Cuando se sospecha que la cuenta nunca cambió su contraseña de fábrica, o usa una contraseña débil típica. Es el punto de partida recomendado en DVWA, donde la cuenta admin suele tener contraseña por defecto password.
Credential stuffing Usa pares usuario+contraseña ya filtrados de otro sitio, apostando a que la persona los reutiliza. Cuando se cuenta con una lista de credenciales filtradas legítimas (de un laboratorio de concientización, por ejemplo) y se quiere probar reutilización de contraseñas. Requiere que esas credenciales correspondan al mismo propietario del objetivo.
Password spraying Prueba una misma contraseña común contra muchas cuentas distintas, para no disparar bloqueos por intentos repetidos en una sola cuenta. Cuando hay varias cuentas de usuario conocidas (por enumeración previa) y se sospecha una política de contraseña débil compartida, en vez de atacar una sola cuenta con muchos intentos.

Para esta práctica contra DVWA se usa ataque de diccionario: es el escenario más realista para un panel de login recién desplegado con credenciales de fábrica sin cambiar, y es el que menos ruido genera.

2. Armado del diccionario

El diccionario se separa en dos listas: usuarios y contraseñas. Para DVWA, el usuario admin es conocido de antemano (no hace falta enumerarlo), así que el diccionario se concentra en contraseñas comunes y de fábrica. 

# Lista de usuarios (DVWA expone "admin" por defecto)
cat > users.txt <<EOF
admin
EOF

# Lista de contraseñas: fábrica/comunes primero
cat > passwords.txt <<EOF
password
admin
123456
letmein
dvwa
EOF

Si el entorno tiene SecLists instalado, es preferible partir de una lista curada de credenciales por defecto en vez de escribirla a mano: 

# Verificar si existe la lista de credenciales por defecto de SecLists
ls /usr/share/seclists/Passwords/Default-Credentials/ 2>/dev/null
Regla de priorización. Empezar siempre por contraseñas de fábrica y comunes (ataque de diccionario) antes de escalar a listas más grandes. Un diccionario de 5–20 entradas suele bastar para confirmar si la falla "contraseña de fábrica" existe en DVWA; no hay necesidad de arrancar con una lista de miles de palabras.

3. Comando de Hydra contra el login (http-post-form)

El formulario de login de DVWA envía un POST a /login.php con los campos username, password y un botón Login. Antes de lanzar Hydra, hay que confirmar el texto que distingue un intento fallido (por ejemplo, DVWA responde "Login failed" en la página cuando la credencial es incorrecta). 

# Sintaxis general del módulo http-post-form:
#   hydra -L <usuarios> -P <contraseñas> <host> http-post-form \
#     "<ruta>:<campo_user>=^USER^&<campo_pass>=^PASS^&Login=Login:<cadena_de_fallo>"

hydra -L users.txt -P passwords.txt 127.0.0.1 http-post-form \
  "/dvwa/login.php:username=^USER^&password=^PASS^&Login=Login:F=Login failed" \
  -t 4

Notas sobre la sintaxis:

  • -L/-P: listas de usuarios y contraseñas (-l/-p para un valor único).
  • ^USER^ / ^PASS^: marcadores que Hydra sustituye por cada combinación probada.
  • F=Login failed: cadena que aparece cuando el intento falla. Alternativamente, S=... marca una cadena que aparece solo cuando el intento tiene éxito (por ejemplo, un fragmento del encabezado del panel autenticado).
  • -t 4: 4 tareas en paralelo — ver sección 5 sobre límites anti-DoS antes de subir este número.
Cookie de sesión de DVWA. DVWA suele requerir una cookie de sesión PHP válida (PHPSESSID) presente antes de aceptar el POST de login, y a veces un token CSRF (user_token) que cambia en cada carga del formulario. Si Hydra no obtiene éxito con ningún intento, verificar primero si el formulario exige ese token — en ese caso, Hydra necesita el parámetro adicional o un script auxiliar que renueve el token antes de cada intento.

4. Cómo se ve un intento exitoso

Cuando Hydra encuentra una combinación válida, la imprime en su salida estándar con el formato siguiente: 

[DATA] max 4 tasks per 1 server, overall 4 tasks, 5 login tries (l:1/p:5), ~2 tries per task
[DATA] attacking http-post-form://127.0.0.1:80/dvwa/login.php:username=^USER^&password=^PASS^&Login=Login:F=Login failed
[80][http-post-form] host: 127.0.0.1   login: admin   password: password
1 of 1 target successfully completed, 1 valid password found
Hydra finished at 2026-11-24 10:09:47

La línea clave es [80][http-post-form] host: ... login: ... password: ...: ahí aparece el par usuario/contraseña válido. Para documentar el hallazgo con el mismo vocabulario que usaría un analista de Blue Team leyendo un log de autenticación, este resultado se traduce al patrón de intentos fallidos seguidos de uno exitoso: 

10:02:11 FAILED login user=admin from 127.0.0.1
10:02:12 FAILED login user=admin from 127.0.0.1
10:02:12 FAILED login user=admin from 127.0.0.1
...
10:09:47 SUCCESS login user=admin from 127.0.0.1   (password=password)

5. Límites anti-DoS (acotado, con pausas)

El objetivo de esta práctica es confirmar la existencia de la falla (contraseña de fábrica sin límite de intentos), no saturar el servidor de DVWA ni generar una denegación de servicio. Reglas prácticas:

ParámetroQué controlaValor recomendado en laboratorio
-t Número de tareas/hilos en paralelo. 2–4 para una prueba acotada contra un solo objetivo local.
-w Tiempo de espera (segundos) por respuesta antes de reintentar. 20–30, para dar pausas entre intentos y no saturar el servidor.
Tamaño del diccionario Cuántas combinaciones se prueban en total. Acotado (5–20 contraseñas) mientras se confirma el ataque de diccionario; no usar listas de miles de entradas en esta fase. 
# Comando acotado, con pausas, para un laboratorio local (recomendado):
hydra -L users.txt -P passwords.txt 127.0.0.1 http-post-form \
  "/dvwa/login.php:username=^USER^&password=^PASS^&Login=Login:F=Login failed" \
  -t 4 -w 30
Señal de detener la prueba. Si el servidor de DVWA empieza a responder con latencia creciente, errores 5xx, o deja de responder, detener la ejecución de inmediato. Esa reacción es evidencia de que la prueba está afectando la disponibilidad del servicio, lo cual excede el objetivo de "confirmar la falla" y se convierte en una denegación de servicio no buscada, incluso en un laboratorio propio.

6. Resumen del flujo

  1. Confirmar que el objetivo (DVWA) está en el alcance autorizado.
  2. Elegir el tipo de ataque: diccionario, para credenciales de fábrica.
  3. Armar users.txt y passwords.txt acotados.
  4. Identificar la cadena de fallo/éxito del formulario de login.
  5. Ejecutar Hydra con http-post-form, concurrencia baja y pausas (-t 4 -w 30).
  6. Leer la línea [80][http-post-form] ... login: ... password: ... de la salida y documentar el hallazgo como par FAILED×N → SUCCESS.
  7. Detener la prueba ante cualquier señal de degradación del servicio.
